# DECISIONS.md

## Вариант
Вариант 1: изменяемый аспект — максимальное количество позиции, параметр 10 (в базовом задании было 100).
Значение хранится только в константе `OrderItem.MAX_QUANTITY`. Диапазон 1..10 проверяется в одном методе `OrderItem.checkQuantity`,
а при объединении повторной позиции итоговое количество проверяется в `OrderItem.increase`.

## Решение 1. Инварианты защищены в конструкторах, состав заказа меняется только через Order
Все поля `private`, `Product`, `Employee` неизменяемы (`final`), `OrderItem` меняет только количество через `increase`.
`Order.getItems()` возвращает неизменяемую копию списка, поэтому внешний код не может обойти правила через `getItems().add(...)`
или `clear()`. Альтернатива — вернуть сам список `items`, как в исходном фрагменте. Это нарушило бы правило «после confirm заказ
неизменяем» и правило объединения строк, так как их можно было бы обойти снаружи.

## Решение 2. Итог не хранится, состояние управляется статусом
`Order.total()` каждый раз считает сумму из текущих строк, поэтому она не может разойтись с составом заказа после add/remove.
Запрет изменений после подтверждения реализован одним приватным методом `requireDraft()`, который вызывают add, remove и confirm.
Статус — перечисление `OrderStatus` (DRAFT, CONFIRMED), а не boolean, чтобы состояния можно было расширить.
Альтернатива — поле `total`: оно требует обновления в каждом методе и легко устаревает.

## Анализ фрагмента
`public List<OrderItem> getItems() { return items; }` отдаёт наружу изменяемую внутреннюю коллекцию. Вызывающий код может сделать
`order.getItems().add(new OrderItem(p, 50))`, `remove` или `clear` в обход `addProduct`, проверки количества, объединения и запрета
изменений после confirm. Исправление: `Collections.unmodifiableList(new ArrayList<OrderItem>(items))`; проверка в SelfCheck:
`getItems().clear()` бросает `UnsupportedOperationException`, и состав заказа не меняется.
